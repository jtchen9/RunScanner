# Robot Mobility Calibration and Preflight Guide

Updated: 2026-10-19

## 1. Current system

The upgraded robots use:

- all-metal TT motors;
- the original low-cost Mecanum wheels;
- 9 V motor-HAT input;
- the `balanced_timed_v2` drivetrain model;
- no forward startup kick;
- no turn startup kick;
- gyro heading hold during forward movement;
- separately calibrated flat-floor and bump-crossing speeds and timing.

The active calibration program is:

```bash
TestGyro/robot_mobility_calibrate.py
```

The following are retained only as old reference versions and should not be used for new fleet calibration:

```text
TestGyro/robot_mobility_calibrate_v1.py
TestGyro/robot_mobility_calibrate_v2.py
```

Production calibration is stored in:

```text
/opt/_RunScanner/robot_mobility_calibration.json
```

The registry is not changed until the operator reviews the final summary and explicitly accepts the write.

## 2. Measurement conventions

Use these conventions consistently whenever the programs request physical measurements:

- Distance: centimetres.
- Heading error: CCW/left is positive; CW/right is negative.
- Lateral displacement: left is positive; right is negative.
- Turn cumulative error: positive means overshoot; negative means undershoot.

## 3. Health checks before calibration

### 3.1 Check the I²C devices

The expected devices are:

- `0x10`: motor HAT;
- `0x68`: IMU.

Run ten checks:

```bash
cd /opt/_RunScanner

for i in {1..10}; do
    echo "Check $i"
    i2cdetect -y 1 | grep -E '(^| )10 |(^| )68 '
    sleep 1
done
```

Both addresses should appear in all ten checks.

### 3.2 Run static preflight

```bash
python3 TestGyro/robot_mobility_preflight.py --static-only
```

This checks:

- production calibration loading;
- repeated motor-HAT communication;
- stationary gyro health;
- front camera health;
- rear camera health;
- location pipeline execution.

Both `front.ok=true` and `rear.ok=true` are required. The location command may report an overall result using only one camera, but preflight must fail if either declared camera is unavailable.

If a camera fails, first verify that it is plugged in before investigating software.

## 4. Run calibration

```bash
cd /opt/_RunScanner
python3 TestGyro/robot_mobility_calibrate.py
```

The program asks whether to calibrate each item. Answering `n` preserves the current production value for that item.

An operator-rejected result repeats only that calibration item. Earlier accepted sections remain in memory. Pressing `Ctrl-C`, a program exception, or a hardware failure still terminates the session without writing the unfinished calibration.

### 4.1 Stationary gyro bias

The robot must remain completely stationary.

The program performs three measurements and reports the mean `GZ_BIAS`, within-test spread, between-test spread, and sample count. Accept only a stable and repeatable result.

### 4.2 Flat-floor forward PWM balance

The program starts with production values, normally near PWM 30.

For each trial:

1. Enter right/M1 PWM.
2. Enter left/M2 PWM.
3. Run the five-second flat-floor trial.
4. Observe smoothness, heading error, and lateral displacement.
5. Accept the pair or enter a revised pair.

The goal is smooth forward movement with minimal heading and lateral error. Do not force all robots to use the same pair. Motor, wheel, load, and chassis differences can require different values.

PWM values around 29–33 are currently normal for the upgraded fleet. No startup kick is required when all four wheels start immediately.

### 4.3 Flat-floor distance timing

The program runs two timed trials and asks for measured distance in centimetres. It calculates seconds per metre and performs a 1.0 m verification.

Accept only when all wheels start immediately, motion is smooth, there is no persistent zig-zag, and distance, heading, and lateral displacement are acceptable.

### 4.4 Turning calibration

Current turn PWM is normally 30 with no startup kick.

The program runs:

1. ten zero-margin CCW turns;
2. ten zero-margin CW turns;
3. calculation of separate CCW and CW stop margins;
4. ten compensated CCW turns;
5. ten compensated CW turns.

Enter physical cumulative error using positive for overshoot and negative for undershoot. Reject any result showing hesitation, pivoting around a stuck wheel, abnormal sound, or inconsistent physical turns.

### 4.5 Bump-crossing PWM balance and timing

The two directions are calibrated separately:

- `+Y`: inner room to outer room;
- `-Y`: outer room to inner room.

The program uses this movement order:

1. `+Y` balance/timing trial;
2. `-Y` balance/timing trial;
3. `+Y` 2.0 m verification;
4. `-Y` 2.0 m verification.

For each direction:

1. Enter right/M1 and left/M2 bump PWM.
2. Run a 12-second crossing trial.
3. Confirm that the robot cleared the ramp without stalling or manual assistance.
4. Enter forward distance in centimetres.
5. Enter final heading error, with CCW/left positive.
6. Enter lateral displacement in centimetres, with left positive.
7. Accept the balance and timing or reject it and enter a revised PWM pair.

Adjustment guidance:

- positive CCW/left heading error: consider decreasing right/M1 or increasing left/M2;
- negative CW/right heading error: consider increasing right/M1 or decreasing left/M2.

Rejecting a direction repeats that direction’s PWM-balance and timing item while preserving earlier calibration sections. Rejecting verification returns to the complete balance/timing/verification item for that direction.

The current fleet normally uses bump PWM near 40/40. A robot-specific pair such as 40/39 is acceptable when physically verified.

### 4.6 Final review and save

Review the complete JSON summary carefully. Only then answer yes to:

```text
Write this calibration to the production registry?
```

If the answer is no, the production registry remains unchanged.

## 5. Check the active calibration

```bash
python3 TestGyro/robot_mobility_calibrate.py --check
```

Confirm the active model, flat-floor PWM and timing, turn PWM and stop margins, and both directions’ bump PWM and timing.

Legacy `distance_model`, `short_move`, and `move_startup` fields remain for rollback. They are not used for normal `balanced_timed_v2` motion.

## 7. Preflight tests

### 7.1 Static-only preflight

```bash
python3 TestGyro/robot_mobility_preflight.py --static-only
```

Use this for a quick health check without moving the robot.

### 7.2 Standard flat-floor preflight

```bash
python3 TestGyro/robot_mobility_preflight.py
```

This adds:

- lifted one-second forward wheel-direction test;
- attended 0.10 m startup move;
- measured 1.00 m flat-floor move;
- four alternating `+90°/-90°` turn cycles;
- post-motion motor-HAT, gyro, camera, and location checks.

For the 1.00 m measurement, enter distance in centimetres, heading error with CCW/left positive, and lateral displacement in centimetres with left positive.

### 7.3 Full preflight with bump crossing

```bash
python3 TestGyro/robot_mobility_preflight.py --with-bump
```

This runs the complete standard preflight plus:

1. inner-to-outer 2.00 m crossing;
2. outer-to-inner 2.00 m crossing.

For each direction, record measured distance in centimetres and confirm that the robot clears the ramp without stalling, internal fighting, or manual assistance.

## 8. Readiness before an overnight test

Before an unattended experiment:

1. Confirm the robot uses `balanced_timed_v2`.
2. Run ten I²C checks and confirm both `0x10` and `0x68` remain present.
3. Run `--with-bump` preflight if the experiment crosses the bump; otherwise run at least standard preflight.
4. Require both cameras to pass.
5. Confirm all four wheels start immediately and remain engaged.
6. Confirm no abnormal sound, hesitation, or repeated zig-zag.
7. Confirm the large motor battery and Pi/camera power are on.
8. Complete the separate NMS-side health check.
9. Review the generated report and require `PREFLIGHT PASS`.

## 9. Troubleshooting

### 9.1 `Errno 121` or `Remote I/O error`

This indicates an I²C communication failure:

- `0x10`: motor HAT;
- `0x68`: IMU.

Run the ten-check command in Section 3.1. If either address is missing or intermittent:

1. stop calibration and movement;
2. check power, ground, SDA/SCL wiring, and connectors;
3. power-cycle the robot if necessary;
4. repeat the ten checks;
5. run static preflight again.

Possible contributors after the motor upgrade include startup-current transients, PWM/brush noise, ground disturbance, wiring vibration, and loose connectors. One isolated event does not prove the motors are responsible; record whether failure occurs before startup, exactly at startup, during movement, or after stopping.

### 9.2 Camera failure

Check physical connection first, then inspect enumeration:

```bash
ls -l /dev/v4l/by-id/
v4l2-ctl --list-devices
lsusb
```

Do not approve a robot for overnight operation unless both declared cameras pass.

### 9.3 Calibration interrupted before final save

The production registry remains unchanged. Restart calibration and reuse the last physically validated values as initial entries. Skipping an item uses the existing production value, not an unfinished value from the interrupted session.

## 10. Operational principle

Calibration establishes robot-specific parameters. Preflight determines whether the robot is healthy now. Both are required:

- a good calibration does not prove that cameras, I²C devices, wheels, and power are healthy today;
- a passing preflight does not replace calibration after changing motors, wheels, payload, supply voltage, or chassis geometry.

Once calibration and preflight are acceptable, proceed to the actual experiment rather than continuing to optimize small differences without evidence of an operational problem.
